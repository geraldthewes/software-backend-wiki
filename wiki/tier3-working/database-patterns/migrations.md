# Database Migrations

> **Tier 3** | Source: Alembic docs, golang-migrate docs | Enforces/Derives From: wiki/tier1-sources/swebok-v4/ka06-operations.md, wiki/tier2-core/twelve-factor-app/factors.md

## Summary

Migrations are version-controlled, reversible schema changes. They ensure that every environment — development, staging, production — runs the same schema, and that schema evolution is auditable and reproducible.

## Why Migrations

- Track schema changes in version control alongside application code.
- Reproducible environments: any developer can apply all migrations from scratch.
- Team coordination: no more "just run this ALTER TABLE on the server."
- Rollback: every migration must have a corresponding down migration.

## Python: Alembic

Alembic is the standard migration tool for SQLAlchemy-based projects.

### Setup

```bash
pip install alembic
alembic init alembic
```

This creates `alembic.ini` and an `alembic/` directory with `env.py` and a `versions/` folder.

Configure `alembic.ini`:
```ini
sqlalchemy.url = postgresql://user:pass@localhost/mydb
```

Or use an environment variable in `env.py`:
```python
import os
config.set_main_option("sqlalchemy.url", os.environ["DATABASE_URL"])
```

### Common Commands

```bash
# Generate a migration by comparing models to the DB schema
alembic revision --autogenerate -m "add users table"

# Apply all pending migrations
alembic upgrade head

# Roll back the most recent migration
alembic downgrade -1

# Roll back to a specific revision
alembic downgrade abc123

# Show current revision
alembic current

# Show migration history
alembic history --verbose
```

### Review Autogenerated Migrations

Always review autogenerated migration files before applying. Alembic cannot detect:
- Renamed tables or columns (it sees a drop + add).
- Data migrations (backfilling a new column).
- Partial indexes or complex constraints.

Edit the generated file in `alembic/versions/` before running `upgrade`.

### Example Migration File

```python
"""add users table

Revision ID: 0001
Revises:
Create Date: 2025-01-01 00:00:00
"""
from alembic import op
import sqlalchemy as sa

def upgrade() -> None:
    op.create_table(
        "users",
        sa.Column("id", sa.Integer, primary_key=True),
        sa.Column("name", sa.String(255), nullable=False),
        sa.Column("email", sa.String(255), nullable=False, unique=True),
        sa.Column("created_at", sa.DateTime, server_default=sa.func.now()),
    )

def downgrade() -> None:
    op.drop_table("users")
```

## Go: golang-migrate

golang-migrate manages raw SQL migration files, language-agnostic.

### Migration File Convention

```
migrations/
  000001_create_users.up.sql
  000001_create_users.down.sql
  000002_add_email_index.up.sql
  000002_add_email_index.down.sql
```

Always write both up AND down migrations. A migration without a down file is a one-way door.

### Example Files

```sql
-- 000001_create_users.up.sql
CREATE TABLE users (
    id         SERIAL PRIMARY KEY,
    name       VARCHAR(255) NOT NULL,
    email      VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- 000001_create_users.down.sql
DROP TABLE IF EXISTS users;
```

### Commands

```bash
# Install
go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest

# Apply all pending migrations
migrate -database "$DATABASE_URL" -path ./migrations up

# Roll back one migration
migrate -database "$DATABASE_URL" -path ./migrations down 1

# Show current version
migrate -database "$DATABASE_URL" -path ./migrations version
```

## Migration Best Practices

### Never Auto-Migrate on App Startup in Production

```python
# BAD — runs in every process, every deployment restart
if __name__ == "__main__":
    Base.metadata.create_all(engine)  # or alembic upgrade head

# GOOD — migrations are a separate admin step (12-Factor Factor XII)
# Run: alembic upgrade head  (before deploying new app version)
# Then: deploy new app
```

Auto-migration in startup causes:
- Race conditions when multiple instances start simultaneously.
- Silent schema changes that haven't been reviewed.
- Impossible to roll back if startup migration fails halfway.

### Each Migration Must Be Reversible

If a schema change cannot be reversed, document it explicitly and get explicit approval before applying.

### Zero-Downtime Schema Changes: Expand-Contract Pattern

For live systems, never change a column in a single migration. Use the three-phase expand-contract pattern:

**Phase 1 — Expand** (deploy with old app version still running):
```sql
ALTER TABLE users ADD COLUMN email_new VARCHAR(255);
```

**Phase 2 — Migrate** (dual-write in application code, then backfill):
```sql
UPDATE users SET email_new = email WHERE email_new IS NULL;
ALTER TABLE users ALTER COLUMN email_new SET NOT NULL;
```

**Phase 3 — Contract** (after old code is fully removed):
```sql
ALTER TABLE users DROP COLUMN email;
ALTER TABLE users RENAME COLUMN email_new TO email;
```

### Dangerous Operations — Handle with Extra Care

| Operation | Risk | Safe Approach |
|-----------|------|---------------|
| Renaming a table or column | Old code breaks immediately | Expand-contract pattern |
| Dropping a column | Irreversible data loss | Add application code removal first, then drop |
| Changing column type | May truncate data, breaks existing queries | Add new column, migrate, drop old |
| Adding NOT NULL without default | Fails on any non-empty table | Add nullable first, backfill, then add constraint |

### Test Migrations on Production-Sized Data

A migration that takes 2 seconds on 1,000 rows may take 4 hours on 100 million rows. Always test:
1. Run `EXPLAIN ANALYZE` on any table-rewriting statement.
2. Test against a production-sized clone before applying.
3. For large tables, use online DDL tools (e.g., `pt-online-schema-change` for MySQL, `pg_repack` for PostgreSQL).
